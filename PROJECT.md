## Why This Exists

The project exists because a runtime that completes cleanly can still fail to
produce capable, persistent, socially meaningful actors. In the 2026-06-04
60-cycle GPT-5.4 Mini run, the runtime reported `passed`, but the actor kept a
stale shared-storage focus for all 60 cycles, created no substantive PlanBeads,
and never selected `author_mineflayer_action`. Earlier research directions also
made prediction or observer legibility the center even though a positive result
would have said little about capable autonomous actors living together. These
incidents showed that runtime health, individual Minecraft competence, goal
continuity, social opportunity, and scientific claims must be separated.

## Pillars

1. The research object is the long-run behavior of individually capable,
   persistent actors pursuing ActorSoul/LifeGoal-grounded goals in a shared
   Minecraft world. This does not mean optimizing a generic Minecraft score,
   a fastest tech tree, or a race to diamonds.
2. Social behavior must arise under materially interdependent economic,
   cooperative, or quest conditions that give actors reasons to affect one
   another. This does not mean scripting trust, cooperation, specialization,
   conflict, institutions, or any other social conclusion.
3. Minecraft truth belongs to typed runtime state, Mineflayer execution,
   verifiers, and linked artifacts. This does not mean provider prose, memory,
   PlanBeads, screenshots, video, scenario text, or tool names can prove
   physical progress.
4. The program is phenomenon-first: credible long-run observations select
   narrow controlled studies. This does not mean anecdotes become claims, or
   that the project must keep a preselected hypothesis when the observed
   behavior points elsewhere.
5. The repository should make the work inspectable as both exploratory
   research and a public technical portfolio. This does not mean clean
   infrastructure, extensive schemas, compelling video, or polished reports
   are themselves the research contribution.

## Non-Goals

- Do not restore V3 lived-vs-told prediction, V2 co-actor legibility, or WAM as
  the active headline. A mechanism may return only when a newly observed
  phenomenon makes it useful.
- Do not build a Voyager clone, fastest-tech-tree benchmark, house-building
  architecture, hidden Minecraft planner, or pre-committed village simulator.
- Do not scale actor count, role complexity, model heterogeneity, or
  society-level claims to hide weak individual capability or unattributable
  interactions. Re-evaluate scale after capability, continuity, response-window,
  and observability gates have current-run evidence.
- Do not begin model training, fine-tuning, VLA integration, or visual-policy
  replacement while the current tool/runtime path remains the cheaper
  explanation for failure. Re-evaluate only when artifact-complete runs isolate
  a model or action-representation limit that the bounded runtime cannot repair.
- Do not require a large benchmark dataset or gold trajectory corpus before
  declared state predicates and scenario manifests prove insufficient.
- Do not treat verification, logs, screenshots, video, benchmark plumbing, or
  provider usage accounting as a novel contribution. They remain mandatory
  audit hygiene.

## Judgment Rules

1. When provider narrative conflicts with runtime evidence, choose runtime
   evidence and record the contract or evidence failure. The stale-focus live
   runs showed that plausible text and a clean exit can hide behavioral failure.
2. When a social interpretation conflicts with missing capability or continuity
   controls, repair or extend the missing gate before interpreting the run. V4
   was adopted to stop incompetence and goal loss from masquerading as social
   behavior.
3. When scenario usefulness conflicts with actor freedom, create stronger
   material pressure but leave the response open. A scenario may make exchange
   useful; it may not require trust, reciprocity, refusal, or cooperation.
4. When a compelling observation conflicts with recurrence or alternative
   explanations, keep it as a candidate phenomenon. Promote it only after a
   user or delegated reviewer selects it and a controlled follow-up can name a
   baseline, falsifier, competence control, and weakening evidence.
5. When existing implementation conflicts with research value,
   falsifiability, or current evidence, replace the implementation and preserve
   the old shape only as explicit audit trail. AI implementation labor is
   treated as near zero; code volume and sunk cost carry no authority.
6. When ambition conflicts with scarce provider tokens, quota, recorded
   evidence, data integrity, or user attention, choose the smallest
   artifact-complete run that reduces the current uncertainty. Every live
   provider lane requires its exact preflight and approval.
7. When a report could collapse distinct outcomes, keep acting intent, physical
   competence, continuity, social consequence, robustness, efficiency,
   prediction quality, and provider cost separate.
8. When scale conflicts with attribution, begin with the smallest session that
   exposes the interaction and expand only when scale is itself the declared
   experimental variable.

## The Most Important Question Right Now

The project currently risks building a sophisticated social observation layer
around actors that still cannot complete and retain a meaningful long-horizon
Minecraft objective. If an artifact-complete A5 run cannot distinguish model
reasoning failure from provider transport, action-surface, runtime, verifier, or
continuity defects, every later social result remains ambiguous.

Attack this risk with the smallest approval-gated sequence: run the
exact-provider P0 canary, then one complete `prepare_first_iron_batch` A5 case with
`alibaba-model-studio-api:qwen3.8-max-preview`, preserving declaration, raw and
normalized reports, milestone-first observations, workspace refs, usage, and
failure attribution. Only after a selected configuration has current Stage 1
evidence should the project exercise live B3 continuity and then a small C2/C3
multi-actor session.

## Project-Wide Done Criteria

A work unit is done only when all applicable conditions hold:

- The change follows `SPEC.md`, `AGENTS.md`, this intent digest, and the active
  V4 plan without silently reviving historical authority.
- Targeted Detroit-style tests reject the relevant fake-success or hidden-
  dependency case.
- Repo TypeScript changes pass `cd probe && bun run typecheck` and the relevant
  `cd probe && bun test ...`; a completed implementation-plan step also passes
  the full `cd probe && bun test`.
- Documentation changes pass `git diff --check`; changes to public docs or their
  navigation also pass `cd docs && npm run build`.
- Behavior claims cite a fresh provider-free or approved live command and
  current-run artifacts. Unit tests, clean exit, screenshots, video, or provider
  prose alone do not prove behavior.
- Provider-backed work records the exact provider/model, whole-run estimate,
  current-window preflight, approval status, limits, usage, and stop reason.
- Schema or contract changes update their producer, validator, tests, readers,
  reports, and governing docs coherently, without active compatibility aliases
  that preserve a wrong-shaped design.
- Important completed work is committed in a scoped commit with `Why:`,
  `What changed:`, and `Validation:`; unrelated user changes remain untouched.
